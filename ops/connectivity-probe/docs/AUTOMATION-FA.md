# استقرار خودکار probe روی ابر آروان (مرحلهٔ اول: ابزار و آزمون با API ساختگی)

> **وضعیت: هنوز هیچ سروری ساخته نشده، هیچ هزینه‌ای ایجاد نشده و هیچ Secret واقعی درخواست یا استفاده نشده است.**
> تمام منطق فقط با یک **API ساختگی محلی** آزمون شده است. این آزمون‌ها درستی *منطق* ما را ثابت می‌کنند (تلاش مجدد، انقضا، پاکسازی، سقف هزینه)، **نه** اینکه آروان دقیقاً مثل شبیه‌ساز رفتار می‌کند. شکل واقعی API فقط با «dry-run» روی API واقعی تأیید می‌شود (بخش ۷).

## ۱. روش کار
همه‌چیز با GitHub Actions اجرا می‌شود (از محیط ابری Claude نمی‌شود SSH زد یا به آروان رسید). سه workflow:

| workflow | چه می‌کند | چه زمانی |
|---|---|---|
| `Probe trial` | `dry-run` (فقط خواندن)، `deploy`، `collect`، `destroy` | فقط با فشردن «Run workflow» توسط یک انسان |
| `Probe cleanup` | هر ۳ ساعت منابع منقضی‌شدهٔ `jm-probe-*` را پیدا و حذف می‌کند | زمان‌بندی‌شده؛ بدون Secret هیچ کاری نمی‌کند و موفق است |
| `Probe collect` | روزانه گزارش‌های آزمون را از سرور می‌گیرد و خلاصه می‌کند | زمان‌بندی‌شده؛ بدون سرور یا Secret هیچ کاری نمی‌کند |

هیچ‌کدام با `pull_request` اجرا نمی‌شوند، پس Secret به شاخه‌های دیگران نمی‌رسد. ورودی‌ها از طریق متغیر محیطی به برنامه می‌رسند، نه متن shell. آزمون‌های خودکار همین‌ها را بررسی می‌کنند.

## ۲. دسترسی SSH در اجرای چندروزه (اصلاح ۱)
**هیچ کلیدی ذخیره نمی‌شود.** هر دو کلید (کلید کاربر و کلید میزبانِ سرور) با HKDF-SHA256 از همان Secret موجود (`ARVAN_API_KEY`) **مشتق** می‌شوند، با «هدف» جدا (`client` و `host`). پس روز دوم، سوم و … هر اجرا دقیقاً همان کلید را دوباره می‌سازد:
- نه artifact، نه cache، نه فایل در مخزن، نه Secret دوم.
- کلید میزبان هم از Secret مشتق و از طریق cloud-init به سرور داده می‌شود؛ بنابراین هر اتصال با `StrictHostKeyChecking=yes` و **کلید میزبان پین‌شده** انجام می‌شود (اولین-اتصال-را-باور-کن وجود ندارد).
- سرور: کاربر غیر root، ورود با رمز و ورود root خاموش.
- **محدودیت‌ها (صادقانه):** اگر Secret عوض شود، کلیدها هم عوض می‌شوند و SSH به سروری که قبلاً ساخته شده ممکن نیست؛ ولی حذف از طریق API انجام می‌شود و به SSH نیاز ندارد. هر که ARVAN_API_KEY را دارد می‌تواند همین کلید را بسازد؛ این قدرت بیشتری از خود کلید API (که می‌تواند سرور را حذف کند) نیست و سرور آزمایشی هیچ رازی ندارد.
- درستی مشتق‌گیری، قالب OpenSSH (با `ssh-keygen`) و ثابت‌بودن کلید بین اجراها آزمون شده است.

## ۳. پاکسازی مستقل و بدون ادعای «حذف تضمینی» (اصلاح ۲)
`Probe cleanup` به اجرای اصلی وابسته نیست و هیچ حالتی ندارد. زمان انقضا **داخل نام منبع** نوشته می‌شود (`jm-probe-<run>-x<epoch>`)، پس نیازی به ذخیرهٔ وضعیت نیست.
1. همهٔ ناحیه‌ها و همهٔ انواع منبع را فهرست می‌کند (سرور، IP شناور، دیسک، اسنپ‌شات، کلید SSH) و فقط نام‌های `jm-probe-` را در نظر می‌گیرد (منبع دیگران هرگز).
2. منقضی‌ها را حذف می‌کند، سرورها اول. هر حذف تا ۴ دور با فاصلهٔ افزایشی تلاش می‌شود.
3. بعد دوباره فهرست می‌گیرد. **`ok` فقط وقتی درست است که فهرست نهایی همهٔ انواع موفق بوده و چیزی باقی نمانده.** اگر فهرست‌گیری ناموفق باشد، «نامعلوم» است و پاک‌شده حساب نمی‌شود.
4. اگر پاکسازی تأیید نشد، یک **Issue فارسی** در GitHub باز یا به‌روز می‌شود (اعلان ایمیلی GitHub)، و گزارش می‌گوید کدام منبع مانده و در پنل آروان چه باید حذف شود.
5. اجرای `deploy` هم اگر شکست بخورد یا لغو شود، بلافاصله حذف را اجرا می‌کند؛ ولی `Probe cleanup` خط دوم مستقل است.

**محدودیت‌ها:** GitHub ممکن است اجراهای زمان‌بندی‌شده را دیر اجرا یا حذف کند، و در مخزن عمومی بعد از ۶۰ روز بی‌فعالیتی آن‌ها را غیرفعال می‌کند. اگر API آروان از اجراکننده‌های GitHub قابل دسترس نباشد، پاکسازی نمی‌تواند تأیید کند و Issue باز می‌شود. این یک **شبکهٔ ایمنی** است نه تضمین.

## ۴. سقف هزینه بر پایهٔ رفتار تأییدشده (اصلاح ۳)
**تأییدنشده:** آروان وقتی موجودی کیف پول تمام شود چه می‌کند (سرور را متوقف می‌کند؟ بدهی می‌گذارد؟ فقط هشدار می‌دهد؟). پس **کیف پول محدود را سقف قطعی هزینه فرض نمی‌کنیم**؛ فقط یک لایهٔ اضافی و تأییدنشده است.

آنچه واقعاً توسط نرم‌افزار اجرا می‌شود:
- `max_hours` سخت: عدد صحیح ۱ تا ۱۶۸. هر چیز دیگر رد می‌شود. نرخ ساعتی نامعقول (مثلاً با صفرهای اضافه) رد می‌شود.
- **عبارت تأیید** `I-APPROVE-SPEND` برای `deploy`. بدون آن هیچ‌چیز ساخته نمی‌شود.
- فقط **یک** آزمایش همزمان: اگر منبعی با پیشوند `jm-probe-` هست، `deploy` رد می‌شود.
- انقضا در نام منبع + پاکسازِ مستقل هر ۳ ساعت + حذف فوری هنگام شکست.
- سقف نرم‌افزاری گزارش‌شده: `(نرخ + هزینهٔ اضافی) × (ساعات + ۱) × ۱٫۱`. برای ۴۸ ساعت و ۱۳٬۸۶۰ ریال: **۷۴۷٬۰۵۴ ریال** (بدون هزینه‌های اضافی ناشناخته).
- تأخیر پاکسازی هم باید حساب شود: بدترین حالت ≈ `(ساعات + تأخیر پاکسازِ زمان‌بندی‌شده) × نرخ`. تأخیر GitHub تضمین‌شده نیست.

**هنوز ناشناخته (هزینه‌های ممکن خارج از محاسبه):** IPv4 جدا، ترافیک، اسنپ‌شات، گرد کردن ساعتی، مالیات، و اینکه حذف منبع صورتحساب را دقیقاً متوقف می‌کند. اجرای `dry-run` و بررسی صورتحساب بعد از اولین حذف باید این‌ها را روشن کند. **پیشنهاد:** فقط مبلغ تأییدشده را شارژ کنید، اما آن را سقف ندانید.

## ۵. آنچه فقط شما باید انجام دهید (حداقل ممکن)
همه از وب‌سایت‌ها، از گوشی، بدون ترمینال:
1. **تأیید ادغام** PR مربوطه.
2. **پرداخت:** شارژ کیف پول آروان با مبلغ تأییدشده.
3. در پنل آروان یک **کلید API** (Machine User، فقط دسترسی سرور ابری) بسازید و در GitHub: Settings ← Secrets and variables ← Actions ← New repository secret، نام `ARVAN_API_KEY`، مقدار = کلید. **کلید را در چت نفرستید.**
4. **دامنه:** اگر دامنه دارید و DNS آن روی آروان است، `dns=arvan` همه‌چیز را خودکار می‌کند. اگر DNS جای دیگری است، سه رکورد A باید ساخته شود (این کار با ما نیست مگر API آن DNS را بدانیم). بدون دامنه فقط `selfsigned` برای تمرین ممکن است و **آزمون معتبر نیست**.
5. فشردن **Run workflow**: اول `dry-run`، سپس `deploy` با عبارت تأیید.
6. **معرفی آزمونگران** و فرستادن لینک به آن‌ها (آزمون از شبکه‌های ایرانی را هیچ ابزاری جای آن نمی‌گیرد).
7. اگر Issue «هشدار: پاکسازی… تأیید نشد» آمد، حذف دستی منابع `jm-probe-*` در پنل آروان.

## ۶. هزینه (بر پایهٔ ۱۳٬۸۶۰ ریال در ساعت؛ هزینه‌های اضافی شامل نیست)
۲۴ ساعت: ۳۳۲٬۶۴۰ ریال · ۴۸ ساعت: ۶۶۵٬۲۸۰ ریال · ۷ روز: ۲٬۳۲۸٬۴۸۰ ریال. هیچ سرویس پولی جدیدی اضافه نشده است (GitHub Actions رایگان، بدون ابزار یا کتابخانهٔ ثالث؛ فقط `fetch` داخلی Node و ابزارهای خود Ubuntu).

## ۷. آنچه تأیید نشده و در اولین dry-run روشن می‌شود
- مسیرها و بدنهٔ API (`/ecc/v1/...`)، نام فیلدهای پلن و تصویر، نام فیلد IP، پشتیبانی از `init_script` (cloud-init)، کدهای ناحیه.
- مسیر API رکورد DNS آروان (`/cdn/4.0/...`).
- اینکه اجراکننده‌های GitHub (خارج از ایران) به API آروان و به IP ایرانی می‌رسند.
- اینکه سرور آروان به مخزن Ubuntu و Let's Encrypt دسترسی دارد و پورت‌های ۸۰ و ۴۴۳ باز است.
- رفتار صورتحساب (بخش ۴).
هر مورد بالا که با dry-run یا اولین اجرا رد شود، فقط یک فایل (`automation/lib/arvan.mjs`) را تغییر می‌دهد.

## ۸. عیب‌یابی خطای ۴۰۱ (از اولین اجرای واقعی)
اولین dry-run واقعی روی همهٔ درخواست‌ها `401` گرفت. نتیجه‌ها:
- **API از اجراکننده‌های GitHub در دسترس است** (پاسخ HTTP واقعی آمد)؛ مشکل اتصال نیست.
- **۴۰۱ یعنی «کلید شناخته نشد»، نه «نقش کم است».** کمبود نقش (مثل Viewer) معمولاً `403` می‌دهد.
- مستندات آروان در مثال‌های مختلف شکل‌های متفاوتی برای هدر `Authorization` نشان می‌دهند (`Apikey`، `APIKEY`، `API KEY`، و کلید بدون پیشوند). پس کد حالا **شکل پذیرفته‌شده را با درخواست‌های فقط‌خواندنی تشخیص می‌دهد** و فقط همان را به کار می‌برد.
- مقدار Secret پاک‌سازی می‌شود: فاصلهٔ ابتدا و انتها، خط جدید، گیومه، و کلمهٔ `Apikey` که شاید همراه کلید کپی شده باشد.
- اگر باز هم همهٔ شکل‌ها `401` دادند، گزارش dry-run همین را می‌گوید (بدون چاپ کلید) و دلیل‌های محتمل را فهرست می‌کند: کلید نادرست، باطل‌شده یا هنوز فعال‌نشده؛ کلید حساب دیگر؛ یا کلیدی که به IPهای مشخصی محدود شده (تأییدنشده). در این حالت کلید جدید یا بازبینی محدودیت‌های کلید در پنل لازم است. این برنامه **هیچ‌وقت نقش یا دسترسی را خودکار تغییر نمی‌دهد.**
- اگر `403` بیاید یعنی کلید شناخته شد ولی نقش اجازهٔ خواندن ندارد؛ آن‌وقت فقط نقش کاربر ماشینی در پنل باید بازبینی شود.
- اگر خطای احراز هویت رخ دهد، `dry-run` درخواست دیگری نمی‌فرستد، و سایر عملیات (پاکسازی، جمع‌آوری، حذف) با خطای واضح شکست می‌خورند، نه اینکه ساکت بمانند.

## ۹. پاکسازی زمان‌بندی‌شده: «بررسی‌نشده» با «ناموفق» فرق دارد
اجرای واقعی نشان داد در هر شش ناحیه، فهرست سرور و دیسک و اسنپ‌شات کار می‌کند و منبعی با پیشوند `jm-probe-` وجود ندارد؛ ولی دو نوع دیگر فهرست نمی‌شدند: `floating-ips` پاسخ ۴۰۴ می‌داد (مسیرش وجود ندارد) و `ssh-keys` پاسخ ۴۰۳ (نقش فقط‌خواندنی اجازه ندارد). قبلاً هر ناتوانی در فهرست‌کردن «تأییدنشده» حساب می‌شد و پاکسازی هر ۳ ساعت شکست می‌خورد. حالا:
- **نوع‌های لازم** (سرور، دیسک، اسنپ‌شات: چیزهایی که این ابزار می‌سازد و هزینه دارند) باید قابل فهرست باشند؛ وگرنه شکست است و «پاک» اعلام نمی‌شود.
- **نوع‌های اختیاری** (IP شناور، کلید SSH) اگر ۴۰۳ یا ۴۰۴ بدهند، در هر گزارش با عبارت **«بررسی نشد (خطا نیست)»** نوشته می‌شوند و پنهان نمی‌مانند. این ابزار این دو نوع را اصلاً نمی‌سازد (کلید SSH داخل cloud-init می‌رود). اگر در آینده معلوم شود IP شناور جداگانه هزینه دارد، باید مسیر درست آن با فراخوانی فقط‌خواندنی پیدا و به فهرست «لازم» اضافه شود.
- برای پاسخی که دوباره همان جواب را می‌دهد (۴۰۳/۴۰۴) دیگر تلاش و انتظار نمی‌شود؛ فقط خطاهای موقت (۵۰۰، ۴۲۹، قطع شبکه) تکرار می‌شوند.
- هشدار GitHub یک Issue است، نه هر ۳ ساعت یک نظر؛ نظر تازه فقط وقتی اضافه می‌شود که آخرین فعالیت بیش از ۲۰ ساعت پیش باشد. با اولین پاکسازیِ تأییدشده، Issue هشدار خودکار بسته می‌شود. اجرای بدون Secret (رد‌شده) هیچ Issueای را نمی‌بندد.

## ۱۰. آزمون‌ها
`node --test --test-concurrency=1 "test/*.test.mjs"` در `ops/connectivity-probe`. شامل: سقف هزینه، مشتق‌گیری کلید، cloud-init، کلاینت (تلاش مجدد، پنهان‌کردن کلید، رد HTTP ساده)، پاکسازی (فقط منقضی‌های خودمان، تلاش مجدد، گزارش صادقانهٔ ناکامی، فهرست‌ناپذیر = نامعلوم)، دو مرحلهٔ deploy/collect/destroy، CLI، و ایمنی workflowها.
