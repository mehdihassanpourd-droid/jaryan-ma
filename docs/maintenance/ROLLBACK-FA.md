# بازگشت (Rollback) و بازیابی از استقرار ناموفق

> در نصب با بستهٔ آفلاین (`docs/deploy/OFFLINE-DEPLOY-FA.md`) بازگشت برنامه با یک دستور انجام می‌شود: `sudo ./deploy/rollback.sh [--to <نسخه>]` (چک‌سام نسخه را می‌سنجد، فقط برنامه را عوض می‌کند و سلامت را تأیید می‌کند). ارتقای ناموفق خودش به نسخهٔ قبلی برمی‌گردد. دستورهای `git checkout`/`npm ci` زیر مربوط به نصب دستی از مخزن است. تصمیم دربارهٔ پایگاه‌داده همچنان فقط طبق همین سند است.

این سند مکمل `INCIDENT-RESPONSE-FA.md` است و روش به‌روزرسانی در `docs/admin/SELF-HOSTING.md` (بخش ۷) را فرض می‌گیرد: `git pull` ← `npm ci` ← `npm run api:build` ← `prisma migrate deploy` ← `systemctl restart jaryan-api`.

> **قاعدهٔ اصلی:** کد برنامه را می‌شود به‌سادگی به عقب برگرداند، **پایگاه‌داده را نه**. Prisma مایگریشن «برگشت» (down) ندارد و هیچ‌جا در این پروژه مایگریشن را معکوس نمی‌کنیم. هر تصمیمی دربارهٔ پایگاه‌داده با مالک گرفته می‌شود و قبل از آن یک پشتیبان تازه گرفته شده است.

## ۰. پیش از هر استقرار (۵ دقیقه)
1. `npm run ops -- backup` سپس `npm run ops -- backup-verify`. بدون پشتیبان تازه و سالم، مایگریشن اجرا نکنید.
2. نسخهٔ فعلی را یادداشت کنید: `git rev-parse HEAD` (این همان نقطهٔ بازگشت است). بهتر است برچسب بزنید: `git tag deployed-$(date +%Y%m%d-%H%M)`.
3. فهرست مایگریشن‌های جدید را بخوانید: `git diff --stat HEAD..origin/main -- prisma/migrations`. برای هرکدام تعیین کنید «افزایشی» است یا «مخرب» (جدول ۲).
4. وضعیت پایه را ثبت کنید: `curl -s http://127.0.0.1:3001/readyz` و `npm run ops -- reconcile` (فقط‌خواندنی).

## ۱. بازگشت برنامه (بدون تغییر پایگاه‌داده)
مناسب وقتی: خطا فقط در کد است، و مایگریشن جدید نبوده یا فقط افزایشی بوده.

```bash
cd /opt/jaryan-ma
sudo -u jaryan git checkout <نسخهٔ قبلی>      # همان commit یادداشت‌شده
sudo -u jaryan npm ci
sudo -u jaryan npm run api:build
sudo systemctl restart jaryan-api
curl -s http://127.0.0.1:3001/readyz            # باید ready:true باشد
npm run ops -- health                           # کد خروج ۰ یا ۲ قابل‌قبول؛ ۱ یعنی هنوز خراب
```
- مایگریشن افزایشی (ستون/جدول/اندیس جدید) را **برنمی‌گردانیم**؛ نسخهٔ قبلی برنامه آن را نادیده می‌گیرد. `readyz` ممکن است `migrations` را در حالت «اعمال‌نشده» نشان ندهد چون مایگریشن اضافی خطا نیست.
- اگر ستون جدید `NOT NULL` بدون مقدار پیش‌فرض است، نسخهٔ قبلی نمی‌تواند سفارش ثبت کند: این را «ناسازگار» حساب کنید و به بخش ۳ بروید.
- پس از بازگشت: رخداد را باز نگه دارید، علت را بنویسید و تا رفع مشکل دوباره استقرار نکنید.

## ۲. استقرار ناموفق: درخت تصمیم
| مرحله‌ای که شکست خورد | وضعیت واقعی | اقدام |
|---|---|---|
| `npm ci` یا `api:build` | هنوز چیزی راه‌اندازی مجدد نشده؛ سرویس قبلی با کد قبلی کار می‌کند | هیچ‌چیز را restart نکنید. `git checkout <نسخهٔ قبلی>` و دوباره build تا دیسک با سرویس در حال اجرا هم‌خوان باشد. |
| `prisma migrate deploy` (خطا قبل از اجرای هر مایگریشن، مثلاً اتصال) | پایگاه‌داده دست‌نخورده | علت اتصال را رفع و دوباره اجرا کنید. |
| `prisma migrate deploy` وسط یک مایگریشن | PostgreSQL بیشتر دستورهای DDL را در یک تراکنش اجرا می‌کند و معمولاً چیزی نیمه‌کاره نمی‌ماند؛ اما Prisma مایگریشن را «ناتمام» ثبت می‌کند و `/readyz` با `migrations: fail` پاسخ می‌دهد | **۱)** سرویس را restart نکنید. **۲)** با `psql` بررسی کنید دقیقاً چه چیزی اعمال شده. **۳)** اگر هیچ تغییری اعمال نشده: `npx prisma migrate resolve --rolled-back <نام>` و پس از رفع علت دوباره `migrate deploy`. **۴)** اگر بخشی اعمال شده: **دستی ادامه ندهید**؛ به بخش ۳ و تصمیم مالک بروید. |
| `systemctl restart` و سرویس بالا نمی‌آید | مایگریشن‌ها اعمال شده‌اند | `journalctl -u jaryan-api -n 100`. اگر مشکل کد است و مایگریشن افزایشی بود: بخش ۱. اگر ناسازگار: forward-fix (بخش ۳). |
| سرویس بالاست ولی `/readyz` یا `ops health` خراب است | — | `ops health` را بخوانید؛ دیسک، اتصال پایگاه‌داده و مایگریشن را بررسی کنید. |

## ۳. راهبرد بازگشت مایگریشن پایگاه‌داده
**اصل:** مسیر پیش‌فرض «اصلاح رو به جلو» (forward-fix) با یک مایگریشن جدید و بازبینی‌شده است، نه معکوس کردن مایگریشن قبلی.

### انواع مایگریشن
| نوع | مثال | رفتار |
|---|---|---|
| افزایشی و سازگار با نسخهٔ قبلی | ستون nullable، جدول جدید، اندیس جدید | بازگشت برنامه ایمن است؛ مایگریشن را نگه دارید. |
| افزایشی ولی ناسازگار | ستون `NOT NULL` بدون پیش‌فرض، قید یکتایی جدید روی دادهٔ موجود | بازگشت برنامه ممکن است سفارش‌ها را بشکند؛ forward-fix. |
| مخرب | `DROP TABLE/COLUMN`، تغییر نوع، بازنویسی یا ادغام دادهٔ موجود | **هرگز کورکورانه معکوس نکنید.** دادهٔ حذف‌شده با معکوس کردن ساختار برنمی‌گردد و دادهٔ جدید ممکن است از بین برود. فقط با تصمیم مالک و بازیابی از پشتیبان. |

### چه زمانی forward-fix امن‌تر از rollback است
- از استقرار به بعد سفارش، حساب مشتری یا تغییر موجودی با ساختار جدید ثبت شده؛ برگشتن به عقب آن را گم یا خراب می‌کند.
- مایگریشن مخرب یا بازنویسی دادهٔ موجود بوده است.
- نسخهٔ قبلی برنامه با ساختار جدید ناسازگار است.
- مشکل کوچک و محدود است (یک شرط، یک مقدار پیش‌فرض، یک اندیس)، و اصلاح آن سریع‌تر و کم‌خطرتر از بازیابی است.

### چه زمانی rollback کد (و نه مایگریشن) امن‌تر است
- هیچ مایگریشنی نبوده یا فقط افزایشی-سازگار بوده، و خطا فقط در رفتار برنامه است.
- هنوز هیچ دادهٔ حساس جدیدی با رفتار معیوب ثبت نشده یا اثرش با `reconcile` قابل سنجش است.

### بازیابی پایگاه‌داده از پشتیبان (آخرین راه، فقط با تصمیم مالک)
1. سرویس را متوقف کنید تا داده‌ٔ تازه نوشته نشود.
2. از وضعیت فعلی (حتی خراب) یک پشتیبان جدا بگیرید و نگه دارید: ممکن است برای استخراج سفارش‌های جدید لازم شود.
3. پشتیبان انتخابی را **ابتدا در یک پایگاه‌دادهٔ موقت** بازیابی و با `reconcile` و شمارش سفارش‌ها بررسی کنید (`scripts/maintenance/restore-drill.sh`).
4. بدانید همهٔ سفارش‌ها و تغییرات پس از زمان آن پشتیبان از بین می‌روند. فهرست آن‌ها را از پایگاه‌دادهٔ فعلی ذخیره کنید و بعداً با مشتریان هماهنگ کنید.
5. فقط پس از تأیید مالک، روی پایگاه‌دادهٔ تولید بازیابی کنید؛ سپس برنامهٔ سازگار با آن ساختار را بالا بیاورید و `/readyz`، `ops health` و `ops reconcile` را اجرا کنید.
- این مراحل را هرگز ناقص یا بدون پشتیبان دوم اجرا نکنید و `restore-drill.sh` را روی تولید نزنید (خودش رد می‌کند).

## ۴. پس از هر بازگشت یا اصلاح
- `curl /readyz` ← `ops health` ← `ops reconcile` (برای دیدن اثر روی سفارش/موجودی؛ هیچ اصلاح خودکاری وجود ندارد).
- `npm run ops -- log-action --action rollback --outcome success --target release:<id>` و بستن رخداد با شرح علت.
- یک اقدام پیشگیرانه: تست، بررسی مایگریشن در بازبینی، یا تقسیم مایگریشن به دو مرحلهٔ «افزودن» و «حذف» (expand/contract) در انتشارهای جداگانه.

## ۵. چه کارهایی ممنوع است
- معکوس کردن دستی مایگریشن با `DROP`/`ALTER` بدون پشتیبان تازه و بدون تصمیم مالک.
- حذف ردیف‌های `_prisma_migrations` برای «رد شدن» از خطا.
- اجرای `prisma migrate reset` یا `db push --force-reset` روی تولید.
- اصلاح دستی موجودی یا وضعیت سفارش در پایگاه‌داده؛ فقط از طریق پنل مدیریت (تاریخچه و ممیزی دارد).
