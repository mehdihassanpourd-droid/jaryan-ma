# استقرار آفلاین «جریان ما» روی VPS ایرانی (فاز ۲A)

هدف: اجرای کامل فروشگاه روی یک سرور ایرانی **بدون** نیاز به GitHub، npm، Prisma CLI یا هر اینترنت بین‌المللی در زمان نصب و ارتقا. همهٔ مراحل با یک بستهٔ بسته‌بندی‌شده، چک‌سام و اسکریپت‌های بررسی‌شده انجام می‌شود.

> این سند فقط روش را توضیح می‌دهد. تا وقتی دامنه، سرور و تصمیم‌های مالک نهایی نشده، هیچ‌چیز روی سرور واقعی نصب نمی‌شود.

## ۱. محتوای بسته

بستهٔ `jaryan-ma-<نسخه>-linux-x64.tar.xz` (حدود ۳۱ مگابایت با فشردگی پیش‌فرض `-9e`) و فایل `.sha256` کنار آن:

| بخش | توضیح |
|---|---|
| `app/dist/server` | سرور API، ابزار `ops`، ابزار مدیر، ابزار مهاجرت پایگاه‌داده (همه‌چیز در چند فایل bundle) |
| `app/dist/admin` | پنل مدیریت (PWA)، از همان سرور Node سرو می‌شود |
| `app/node_modules` | فقط وابستگی‌هایی که سرور واقعاً import می‌کند (۵۰ بسته، بدون Next.js و ابزار توسعه) |
| `app/prisma/migrations` | فایل‌های SQL مایگریشن (اعمال با ابزار خود بسته، بدون Prisma CLI) |
| `storefront/` | فروشگاه استاتیک ساخته‌شده برای **دامنه‌های شما** (آدرس‌ها هنگام build در آن ثبت می‌شوند) |
| `runtime/node` | Node.js همان نسخه‌ای که بسته با آن ساخته و آزمایش شد (نیازی به نصب Node نیست) |
| `deploy/` | اسکریپت‌های نصب، ارتقا، بازگشت، تأیید، پیکربندی nginx، قالب‌های systemd و env |
| `ops/systemd`, `scripts/maintenance` | تایمرهای پشتیبان و آزمون بازیابی |
| `docs/` | همین مستندات |
| `RELEASE.json` | نسخه، commit، زمان ساخت، آدرس‌های عمومی، فهرست مایگریشن‌ها با چک‌سام، فهرست وابستگی‌ها، چک‌سام lockfile |
| `SHA256SUMS` | چک‌سام تک‌تک فایل‌ها (نصب‌کننده همه را می‌سنجد) |

## ۲. ساخت بسته (بدون ترمینال)

در گوشی یا مرورگر: GitHub ← مخزن ← **Actions** ← **Release package** ← **Run workflow** و چهار مقدار را پر کنید:
نسخه (مثلاً `2026.11.1`)، آدرس فروشگاه، آدرس API، آدرس رسانه (همه `https://…`).
پس از پایان، در صفحهٔ اجرا بخش **Artifacts** فایل‌های `.tar.xz` و `.sha256` را دارد.

- ساخت فقط در GitHub (یا دستگاهی که `npm ci` دارد) انجام می‌شود. **خود بسته هیچ دانلودی لازم ندارد.**
- مقدار `.sha256` را از **کانال دیگری** هم نگه دارید (مثلاً در پیام‌رسان به خودتان) تا اگر فایل در مسیر عوض شد، تشخیص داده شود.

## ۳. پیش‌نیازهای سرور (از مخزن‌های توزیع یا آینه‌های داخلی)

اوبونتو ۲۴٫۰۴ LTS (x86-64) با این بسته‌ها: `postgresql-16`، `nginx`، `curl`، `xz-utils`، `tar`، `coreutils`. Node.js لازم نیست (در بسته است).

**سرور شیء (S3-سازگار) برای تصاویر و snapshotهای کاتالوگ:** این بسته آن را همراه ندارد، چون باید باینری مورد استفاده را خودتان راستی‌آزمایی کنید. با MinIO یا هر سرور سازگار با S3 که آفلاین نصب‌پذیر باشد کار می‌کند. قالب `deploy/systemd/jaryan-minio.service` آدرس‌دهی روی `127.0.0.1` و خاموش بودن کنسول را نشان می‌دهد (این قالب در CI آزمایش نمی‌شود، چون باینری در مخزن نیست). نسخهٔ مناسب و راه تهیهٔ آفلاین آن یکی از «نیازمندی‌های زیرساختی باقی‌مانده» است.

## ۴. نصب اول

```bash
# ۱) بررسی چک‌سام بسته (مقدار را با نسخهٔ ذخیره‌شدهٔ کانال دیگر مقایسه کنید)
sha256sum -c jaryan-ma-2026.11.1-linux-x64.tar.xz.sha256
tar -xJf jaryan-ma-2026.11.1-linux-x64.tar.xz
cd jaryan-ma-2026.11.1-linux-x64

# ۲) پایگاه‌داده (یک بار): نقش و پایگاه‌داده با رمز تصادفی
sudo -u postgres psql -c "CREATE ROLE jaryan LOGIN PASSWORD '…'" -c "CREATE DATABASE jaryan OWNER jaryan"

# ۳) فایل محیطی: الگو را بسازید و CHANGE-ME ها را پر کنید (رمزها، کلیدها: openssl rand -base64 32)
sudo ./deploy/install.sh --package ../jaryan-ma-2026.11.1-linux-x64.tar.xz --init-env
sudoedit /etc/jaryan-ma/api.env

# ۴) آزمایش خشک: چک‌سام‌ها، اعتبار تنظیمات، اتصال به پایگاه‌داده، فهرست مایگریشن‌ها؛ هیچ‌چیز تغییر نمی‌کند
sudo ./deploy/install.sh --package ../jaryan-ma-2026.11.1-linux-x64.tar.xz --dry-run

# ۵) نصب
sudo ./deploy/install.sh --package ../jaryan-ma-2026.11.1-linux-x64.tar.xz

# ۶) مدیر اول (رمز با پرسش مخفی؛ TOTP را با گوشی اسکن کنید)
sudo -u jaryan /opt/jaryan-ma/current/bin/jaryan-admin create --email you@example.ir --role owner

# ۷) سرور شیء: ساخت سطل و سیاست حداقل دسترسی (فقط خواندن images/ و catalog/)
sudo -u jaryan /opt/jaryan-ma/current/bin/jaryan-ops media-setup     # تنظیمات را خودش از /etc/jaryan-ma/api.env می‌خواند

# ۸) nginx (گواهی TLS هر چهار دامنه را قبلاً در /etc/ssl/jaryan/<دامنه>/ بگذارید)
sudo ./deploy/configure-nginx.sh --shop shop.example.ir --api api.example.ir --admin admin.example.ir --media media.example.ir --reload

# ۹) تأیید نهایی (شامل بررسی اینکه آدرس عمومی رسانه چیزی بیش از تصاویر نشان نمی‌دهد)
sudo ./deploy/verify.sh --public-media https://media.example.ir
```

نصب‌کننده به ترتیب: چک‌سام بسته ← باز کردن و سنجش تک‌تک فایل‌ها ← اعتبارسنجی تنظیمات ← وضعیت پایگاه‌داده ← (در ارتقا) پشتیبان و اعتبارسنجی آن ← مایگریشن ← سوییچ نسخه ← راه‌اندازی مجدد ← بررسی سلامت. هر مرحلهٔ قبل از «مایگریشن» که شکست بخورد، هیچ‌چیز را تغییر نداده است.

## ۵. ارتقا

نسخهٔ جدید را همانند بالا بسازید و همان دستور نصب را بزنید. تفاوت‌ها:
- پیش از هر تغییر، **پشتیبان رمزنگاری‌شده گرفته و اعتبارسنجی می‌شود**؛ اگر شکست بخورد ارتقا انجام نمی‌شود (`--skip-backup` فقط آگاهانه).
- هر مایگریشن در یک تراکنش جداگانه اجرا می‌شود؛ شکست یعنی آن مایگریشن کامل برگشته و نسخهٔ در حال اجرا دست‌نخورده است.
- پس از سوییچ، اگر `/readyz` ظرف ۶۰ ثانیه ۲۰۰ نشود، **برنامه خودکار به نسخهٔ قبلی برمی‌گردد** (کد خروج ۲) و در `/var/lib/jaryan-ma/history.log` ثبت می‌شود. پایگاه‌داده برنمی‌گردد.
- نسخه‌های قدیمی (به‌جز جاری و قبلی، و تا ۵ نسخه) خودکار پاک می‌شوند.

## ۶. بازگشت و بازیابی

```bash
sudo ./deploy/rollback.sh --list              # نسخه‌های نصب‌شده
sudo ./deploy/rollback.sh                     # برگشت به نسخهٔ قبلی
sudo ./deploy/rollback.sh --to 2026.11.1      # برگشت به نسخهٔ مشخص
```
بازگشت فقط **برنامه** را عوض می‌کند، پس از سنجش چک‌سام آن نسخه، و سلامت را تأیید می‌کند. **مایگریشن هرگز معکوس نمی‌شود.** اگر نسخهٔ جدید مایگریشن داشت و باید پایگاه‌داده را هم برگرداند، فقط طبق `docs/maintenance/ROLLBACK-FA.md` (اصلاح رو به جلو یا بازیابی از پشتیبان با تصمیم مالک).

بازیابی از پشتیبان و آزمون بازیابی: `jaryan-ops backup-verify`، `scripts/maintenance/restore-drill.sh` و تایمرهای `ops/systemd` (راهنما: `docs/maintenance/SYSTEMD-FA.md`؛ مسیرها اکنون `/opt/jaryan-ma/current/bin/jaryan-ops` است).

## ۷. امنیت رسانهٔ عمومی

دامنهٔ رسانه (`media.…`) روی nginx فقط دو چیز را عبور می‌دهد: `GET/HEAD` برای `/images/*` و `/catalog/*`. این با یک nginx واقعی و سرور شیء ساختگی آزمایش شده است (`server/deploy/nginx-media.test.ts`):

| تلاش | نتیجه |
|---|---|
| تصویر و snapshot کاتالوگ | ۲۰۰ (با هدر `immutable` برای تصاویر) |
| ریشهٔ سطل، لیست‌کردن (`/?list-type=2`)، `/images/` بدون نام | ۴۰۴ |
| هر مسیر دیگر (`/private/…`، `/backups/…`) | ۴۰۴ و حتی به سرور شیء ارسال نمی‌شود |
| API مدیریت سرور شیء (`/minio/admin/…`) و کنسول وب | ۴۰۴؛ کنسول روی پورت جدا، فقط localhost و خاموش |
| `..`، `%2e`، `%2f`، `%00`، فاصله | ۴۰۴ |
| `PUT/POST/DELETE/PATCH` | ۴۰۵ |
| query string (`?acl`، `?versionId`، امضا) | حذف می‌شود؛ به سرور شیء نمی‌رسد |
| کوکی، `Authorization`، `x-amz-*` کلاینت | هرگز ارسال نمی‌شوند |
| پیام خطای XML و هدرهای `Server` / `x-amz-*` / `x-minio-*` | به کلاینت نمی‌رسند |

لایهٔ دوم: سیاست سطل (`jaryan-ops media-setup`) فقط `GetObject` ناشناس روی `images/*` و `catalog/*` می‌دهد (بدون لیست، نوشتن یا حذف)؛ `media-setup --check` دقیق‌بودن آن را می‌سنجد. پشتیبان‌ها هرگز در سطل رسانه نیستند (پوشهٔ `0700` روی دیسک).

میزبان‌ها جدا هستند: روی `api.…` فقط مسیرهای مشتری/عمومی و `/health`؛ روی `admin.…` فقط پنل و API مدیریت؛ `/readyz` فقط از آدرس‌های مجاز (پیش‌فرض localhost).

## ۸. آنچه آزمایش شده و آنچه نشده

آزمایش‌شده (در CI و محلی، **در یک sandbox شبکه بدون اینترنت و بدون DNS**): ساخت بسته؛ نصب روی پایگاه‌دادهٔ خالی؛ ارتقا با پشتیبان و اعتبارسنجی؛ رد بستهٔ آسیب‌دیده/دستکاری‌شده بدون هیچ تغییر؛ ارتقای شکست‌خورده با بازگشت خودکار؛ بازگشت دستی و امتناع از نسخهٔ خراب؛ آزمون بازیابی با ابزارهای خود بسته؛ nginx واقعی.

آزمایش‌نشده: systemd واقعی، TLS و گواهی، سرور شیء واقعی (MinIO)، تایمرها روی سرور واقعی، سخت‌افزار و شبکهٔ VPS ایرانی. فایل‌های مربوط قالب هستند.

## ۹. عیب‌یابی سریع
- `ARCHIVE CHECKSUM MISMATCH`: بسته ناقص دانلود/عوض شده؛ دوباره بگیرید و با کانال دیگر مقایسه کنید.
- `environment file … not valid`: پیام همان لحظه دلیل را می‌گوید؛ تنظیمات اجباری تولید در `.env.example` است.
- `cannot read the database`: PostgreSQL بالا نیست یا `DATABASE_URL` اشتباه است.
- `upgrade failed and the previous release … is running again`: نسخهٔ جدید سالم بالا نیامد؛ `journalctl -u jaryan-api -n 100` را ببینید.
- کد خروج ۳: هر دو نسخه ناسالم‌اند؛ `ROLLBACK-FA.md` بخش ۲.
